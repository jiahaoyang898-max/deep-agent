## 1. 一句话结论

**把深色令牌挂在 `.page`（工作台根节点）作用域上，让全站 `--c-*` 设计令牌沿继承链换肤，从而不重写任何 DOM 就把站内工作台从浅色「静蓝工作台」换成登录页那套「冰川观测站」玻璃语言；验收口径是「真实构建产物 + Playwright 打桩 + 真实合成像素对比度」，当前快照 50 项自动发现元素通过 44 项、6 项未达标，三档宽度零横向溢出、控制台零报错。**

三句话拆开：

- **改了什么**：`ui/src/style.css` 末尾新增一段 `.page { … }` 深色令牌覆盖 + 一批 `.page .原语` 深底重算；`ChatView.vue` 补入摄影背景层（`.backdrop`）、四角取景角标（`.brk`）、底部刻度尺（`.foot`）与 `z-index` 修正；`ChatMessage.vue` 的用户气泡改为白胶囊墨字。
- **为什么**：登录页与站内页此前是两套视觉语言，登录后「从封面掉进一个白底后台」；两者本就该同源，且浅色工作台在深色封面之后出现会破坏「一次登录旅程」的连续性。
- **怎么验**：`npm run build` → `wb_shoot.py`（真实 Vue 组件出图）→ `wb_probe.py`（对比度 / 横向溢出 / 控制台三合一探针），见 §7。

## 2. 架构决策：为什么是「`.page` 作用域令牌层」

### 2.1 三个候选方案

| 方案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **A. 翻 `:root` 全站切换** | 把 `style.css` 的 `:root{--c-*}` 直接改成深色 | 改动量最小，一行不用碰组件 | **不可用**：登录 / 注册页（`cover.css`）复用了 `--c-ink`、`--c-text` 等同一批令牌；`:root` 一翻，封面页的深底卡片会拿到浅色字色，直接崩。此外 `App.vue` 的全局 Toast、启动校验画面也在 `:root` 之下，会被连带翻成深色（本次并不想改它们） |
| **B. 重写 DOM / 复制一套深色组件** | 为 `ChatView.vue` 及其子组件各复制一份深色版本 | 视觉可控性最高 | `ChatView.vue` 单文件 1767 行，加上 `ChatMessage` / `FilePanel` / `SessionInfo` / `CommandPalette` 需要整套双份维护；此后任何功能改动都要改两处，是长期负债 |
| **C. `.page` 作用域令牌覆盖（选用）** | 在 `style.css` 末尾加一段 `.page { --c-*: 深色值 }`，令牌沿继承链下发 | 需要手动补两处「令牌覆盖不到的东西」（见 §4.2、§4.5） | 低。`.page` 之外的一切（登录页、Toast、启动校验画面）天然不受影响 |

### 2.2 为什么 C 能成立：CSS 自定义属性是可继承属性

这是整个方案的技术支点，需要说清两件事：

1. **自定义属性（custom property）参与继承。** `--c-text` 不是「在 `:root` 上算一次就固定」的常量 —— 它是一个沿 DOM 树向下继承的属性值。在 `.page` 上重新声明 `--c-text`，`.page` 子树内所有 `var(--c-text)` 都会解析到新值，包括各组件 `<style scoped>` 里的引用。

2. **Vue 的 `scoped` 不会阻断这条继承链。** `scoped` 只把选择器编译成 `.foo[data-v-xxxx]` 的形式来限定**规则的作用范围**，它不改变元素在 DOM 树里的位置，因此不影响属性继承。所以 `ChatMessage.vue`、`FilePanel.vue` 里 scoped 样式中写的 `var(--c-*)` 会一并换肤 —— 这是「不重写 DOM」能成立的原因。

### 2.3 为什么 `.page` 是唯一正确的挂载点

- `.page`（`ChatView.vue:814`）是工作台根节点，站内所有内容都在它之下；
- 登录页 / 注册页走 `CoverShell.vue` + `cover.css`，用自己的一套 `--cv-*` 令牌，**不在 `.page` 之下**；
- 全局 Toast（`App.vue:122` 的 `.toast-wrap`）挂在应用根，也在 `.page` 之外。

于是 `.page` 恰好是「站内工作台」与「其余部分」的分界线 —— 令牌挂在它上面，作用域天然正确，不需要任何排除逻辑。`style.css:706-726` 的段落注释记录了这条判断。

### 3.5 「填充档 / 文字档」的拆分规则（可复用）

> **规则：当一个语义色同时承担「填充」与「文字」两种身份时，必须拆成两个令牌。**

原因是数学上的，不是审美上的：填充要求**与白色文字**有 4.5:1，文字要求**与深色面板**有 4.5:1。这两个约束在同色相上指向的明度方向相反 —— 满足其中一个必然失守另一个。

设计说明书 §2.1 给出的三档实测（背景取中栏面板合成色 `#373f4d`）：

| 色值 | 深底上作文字 | 结论 |
|---|---|---|
| `--cv-brand` `#5563ff` | ≈ 2.3:1 | 远低于 AA，只能做实心填充 |
| `--cv-brand-lt` `#8b93ff` | ≈ 3.9:1 | 仍不够（在胶囊 / 正文底上落在 3.9–4.5 区间） |
| `--cv-brand-text` `#adb4ff` | 6.21 – 8.85:1 | 深底上品牌色文字的唯一可用档 |

落位：**实心填充**（助手头像底、发送键、文件色标）→ `--c-brand`；**深底上的品牌色文字**（计数徽章、类型胶囊、正文强调数字、链接、焦点环、`li::marker`、`caret-color`）→ 一律 `--c-brand-text`。

## 4. 踩过的坑与修法

每条按「现象 → 根因 → 修法 → 证据」记录。

### 4.1 翻 `:root` 会连带破坏登录 / 注册页

- **现象**：最初按最直觉做法把深色值写进 `:root`，登录页封面立刻出问题 —— 深底玻璃卡片上的文字拿到的还是浅色值。
- **根因**：`cover.css` 与 `style.css` 共用同一批 `--c-*` 令牌（`--c-ink`、`--c-text` 等）。`:root` 是全局作用域，翻它等于同时改两个页面，而封面页的底本来就是深色，它的令牌值是按「深底 + 白字」标定的，再翻一次就反转成「深底 + 深字」。
- **修法**：深色令牌挂在 `.page` 上，不动 `:root`。`.page` 之外（登录页、全局 Toast、启动校验画面）保持原浅色。
- **证据**：`style.css` L706–726 段落注释；`App.vue:122` 的 `.toast-wrap` 与 `CoverShell.vue` 均不在 `.page` 之下。

### 4.2 换令牌 ≠ 换颜色：`.page` 必须自己重设 `color`

- **现象**：只把令牌换成深色、不写 `.page { color: … }`，`.page` 内所有**没有显式写 `color`** 的元素仍然是浅墨色，在深底上大面积失守。
- **根因**：`style.css` L100–110 有 `body { color: var(--c-text); }`。这条规则在**浅色期**于 `body` 上求值，`var(--c-text)` 当时解析为 `#1b2137`，于是 `body` 的 `color` **计算值**就是 `rgb(27,33,55)`。深色令牌挂在 `.page` 上只影响 `.page` 子树内 `var()` 的**解析**，但 `.page` 自己没有 `color` 声明，它的 `color` 是**从 `body` 继承来的那个已算好的 `rgb(27,33,55)`**；继承还会把这个浅色值继续往下传给所有「没显式写 color」的后代。**继承传的是计算值，不是变量引用。**
- **修法**：在 `.page` 里显式写 `color: var(--c-text);`（`style.css:759`），把继承链在这一层截断并重设。
- **证据**：`style.css` L755–759 的注释原话 —— 「换肤换的是令牌，但 color 属性是继承来的」。过程记录：修复前同口径实测的失守项大量落在 3:1 以下（该区间来自改造过程中的探针输出，不是本次 `probe.json` 快照）；补上这一行后，`probe.json` 中绝大多数元素回到 6–15:1 区间。

### 4.3 语义色的「填充 / 文字」双重身份必须拆令牌

- **现象**：品牌色当文字用时整体偏暗，实测远低于 AA。
- **根因**：`--c-brand #5563ff` 在深底上作文字只有 ≈2.3:1（设计说明书 §2.1）。它只能做填充底（白字压在上面）。
- **修法**：新增 `--c-brand-text: #adb4ff`，并把既有的 `--c-brand-deep` 在深色期**改映射到文字档**（因为既有代码里它已被当作「品牌文字」使用）。同时把一批「品牌色当文字」的原语统一改挂文字档：`.page a`、`.page :focus-visible`、`::selection`、`caret-color`、`.md-body li::marker`、`.page .chip-brand`、`.md-body a` 的下划线。
- **证据**：`style.css:762-766`、`style.css:816-822`、`style.css:861-867`、`style.css:869-874`；`probe.json` 中两个品牌色文字项 `SPAN.h-title` 7.71:1、`BUTTON.tab.on` 7.23:1、`CODE.` 6.17:1，均达标。

### 4.4 徽章 / 胶囊用「深色内嵌底 + 语义色描边」，不用半透明语义色填充

- **现象**：初版把计数徽章 / 类型胶囊做成「语义色 14–18% 半透明填充 + 同色系文字」—— 这是很常见的做法 —— 结果对比度反而掉了。
- **根因**：**半透明语义色填充会把局部底色抬亮**，于是背景与同色系文字的亮度趋同。玻璃面板本来就是半透明的，被抬亮的空间更大。设计说明书 §2.2 的实测：品牌色 18% 填充把底从 `#4f5765` 抬到 `#535c84`，同色系文字只剩 **2.39:1**。
- **修法**：四个 `--c-*-soft` 在深色期**统一收敛为同一个深色内嵌底** `rgba(8,12,26,0.5)`，靠 `--c-brand-line` 这类同色相半透明描边 + 文字档文字来表达语义，把局部背景锁死在暗端。
- **证据**：`style.css:765-778`；设计说明书 §2.2 的修正后数字（胶囊底落到 `#171c2a`–`#2d3341`，语义色文字回到 6.2–13.9:1）。当前 `probe.json` 中 `SPAN.num.side-count` 3.5:1 与 `SPAN.count.num` 3.55:1 仍是这一类的残留，但其取样背景 `#545977` / `#535876` 是**亮描边**像素而非填充像素（详见 §8.2 的方法论问题）。

### 4.5 摄影底进场后，三栏被照片盖住（层叠上下文）

- **现象**：加上 `.backdrop` 摄影层后，三栏面板看起来「变透明了」—— 面板内容像是直接压在照片上，同时徽章与按键的对比度全部失守。
- **根因**：`.backdrop`（`ChatView.vue:826`）是 `position:absolute; z-index:0`。**`z-index` 取整数（不是 `auto`）的定位元素会创建层叠上下文**，并且它作为「z-index:0 的定位元素」被画在**非定位内容（in-flow 非定位块）之上**。`.body`（三栏容器，L1131）当时只有 `position:relative` 而 `z-index:auto` —— `z-index:auto` 的 `relative` **不创建层叠上下文**，三栏因此落在照片之下。
- **修法**：给 `.body` 显式 `z-index:1`（`ChatView.vue:1136-1137`），让三栏整体垫到照片之上。`.foot`（底部刻度尺，L1144-1146）同因同样处理。
- **证据**：`ChatView.vue` L1132–1135 的注释完整记录了这条因果链；修好后 `probe.json` 里中栏元素（如 `LI.` 15.03:1、`CODE.language-sql` 12.07:1）才拿到稳定的暗底。

### 4.6 用户气泡刻意保留「白胶囊 + 墨字」

- **现象**：满屏深色里，如果连用户自己的提问气泡也是深色，对话的「我问 / 它答」会失去方向感。
- **根因**：这不是 bug，是**主动设计**。线上原实现是品牌渐变填充的用户气泡 —— 渐变叠渐变是 AI 套路配色，且白字压 `#5563ff` 只有 4.51:1（临界）。
- **修法**：改用登录页 `.pill` 的白底墨字语言（`ChatMessage.vue:245-256`）：`linear-gradient(180deg, rgba(255,255,255,.97), rgba(243,245,255,.93))` + `color:#1b2137`（即 §3.2 里单独保留的 `--c-ink-3`）。它在满屏深色里成为**唯一的实心亮面**，一眼锚定「这句是我说的」。
- **证据**：设计说明书 §2.6 实测 14.88:1（90 分位底）/ 13.39:1（最不利的 10 分位底），两种口径都远超门槛。注意 `probe.json` 里 `DIV.bubble-user` 报 1.61:1 是**取样伪影**，见 §8.2。

#### ⚠ 有两份 `dist`，不要测错目标

项目里存在**两份构建产物**，它们互不自动同步：

| 产物 | 由谁产生 | 落在哪 | 谁在读 |
|---|---|---|---|
| **宿主机 `dist`** | 在 ` deep_agent search\ui` 下执行 `npm run build`（= `vue-tsc -b && vite build`，默认 `outDir` 为 `ui/dist`） | ` deep_agent search\ui\dist\` | **探针**：`wb_shoot.py` 的 `DIST` 常量指向这里，静态托管在 `http://127.0.0.1:8090` |
| **容器镜像内的 `dist`** | `docker compose build frontend`（`docker/frontend.Dockerfile`，`context: .`） | 镜像内，由 nginx 托管 | **浏览器**：`http://localhost:8080`（`docker-compose.yml:97` 的 `8080:80`） |

推论：

- `start.ps1 -FrontendOnly` 走的是 `docker compose build frontend`，**只更新容器镜像里那份**，不会更新 `ui/dist/`。所以**重跑探针必须在宿主机单独执行 `npm run build`**，光跑 `-FrontendOnly` 测到的还是旧产物。
- 反过来也一样：宿主机 `npm run build` 不会改变 8080 上看到的内容。
- 如果确实需要从容器里取产物（例如宿主机不具备构建条件），可用 `docker cp das-frontend:/usr/share/nginx/html <目标路径>` 导出后再指向它；但**默认路径下探针读的就是宿主机 `ui/dist`**，一般不需要这一步。

### 8.4 代码层面的后续建议

1. **`--c-brand-deep` 的语义已经分裂**：浅色期它是「压深档」（`#3f4cd9`），深色期被映射成文字档（`#adb4ff`）。建议确认深色期没有别处把它当填充用；若没有，后续可考虑直接废弃它、统一到 `--c-brand-text`，避免两个令牌指代同一件事。
