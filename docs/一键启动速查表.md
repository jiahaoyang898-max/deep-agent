# 一键启动速查表

> 适用于 Deep Agent Search（站内工作台）·2026-10-15 真机验证通过
> 详细说明见 `README.md` 的启动章节；本页是「打开就能照做」的精简版。

## 一、启动（一条命令）

在**项目根目录**（含 `docker-compose.yml` 的那一层）执行：

| 系统 | 命令 |
|---|---|
| Windows（推荐，双击即可） | 双击 **`start.bat`** |
| Windows（PowerShell 手动） | `powershell -ExecutionPolicy Bypass -File .\start.ps1` |
| macOS / Linux | `bash start.sh` |

> 不想用脚本，等价命令就一行：
> ```bash
> docker compose up -d --build
> ```

**首次**约 3~8 分钟（拉镜像 → 构建 3 个业务镜像 → 起 4 个容器 → 等 MySQL 建库建表 → 逐个探活）。
**之后**再次启动只需十几秒。

### 前置条件（只有两条）
1. **Docker Desktop 已启动**（托盘图标是绿的，不是停止状态）。
2. 磁盘有空间：**D 盘剩余 ≥ 2 GB**；系统盘若不足 5 GB 会弹提醒。

## 三、只改了前端代码？用这个（快得多）

改完 `ui/src/**` 之后**不要重跑全量启动**，只重建前端容器（实测约 40 秒）：

```powershell
powershell -ExecutionPolicy Bypass -File .\start.ps1 -FrontendOnly
```

```bat
start.bat -FrontendOnly
```

```bash
bash start.sh --frontend
```

等价命令：`docker compose build frontend && docker compose up -d frontend`。

## 四、⚠ 改完前端后务必知道的一件事：有两份 dist

这个坑最容易造成「我明明改了，页面怎么没变」：

| 产物 | 在哪 | 谁在读 | 怎么刷新 |
|---|---|---|---|
| **容器内 dist** | 镜像 `/usr/share/nginx/html` | 浏览器打开的 http://localhost:8080 | `start.ps1 -FrontendOnly` |
| **宿主机 dist** | `deep_agent search\ui\dist\` | 自动化验收脚本（截图 / 对比度探针） | 宿主机里 `cd ui && npm run build` |

两者**互不同步**。

- 跑 `-FrontendOnly` **不会**刷新宿主机 `ui/dist` → 验收脚本测到的仍是旧的。
- 宿主机 `npm run build` **也不会**改变 8080 上看到的内容。
- 判断有没有对齐：看 8080 返回的资源 hash 和 `ui/dist/assets/` 里的文件名是否一致。

```bash
# 8080 实际返回的
curl -s --noproxy '*' http://localhost:8080/ | grep -o 'assets/index-[A-Za-z0-9_-]*\.css'
# 宿主机构建出来的
ls ui/dist/assets/
```

本次交付时两边一致：`assets/index-CH_nVbqN.css`。

## 四·五、启动失败案例：backend 镜像构建报 502（已修复）

**现象**：双击 `start.bat` 后脚本报「`[错误] 启动脚本执行失败`」，窗口上方有一大段 `docker compose logs --tail 20` 输出，末尾是：

```
backend.Dockerfile:18
RUN apt-get update && apt-get install -y ... fonts-noto-cjk
E: Failed to fetch http://deb.debian.org/...  502 Bad Gateway
E: Unable to fetch some archives, maybe run apt-get update or try with --fix-missing?
target backend: failed to solve: ... exit code: 100
```

> 注意：日志里 `das-mysql` / `das-auth` 的启动记录是**旧容器**的（时间对不上），不是本次失败的——**失败时容器根本没被重启**，所以 8080 其实还能正常访问，坏掉的只是「重新构建」这一步。

**根因**：`docker/backend.Dockerfile` 要在容器内 `apt-get install` 装 pango / 中文字体，默认直连 `deb.debian.org`，被墙成了 502。本机的 git / pip / npm 都各自配了 `127.0.0.1:7890` 代理，但 **Docker 引擎没有配代理**，所以只有这一步会失败。（`pip` 已经用了清华源，不受影响。）

**已修复**（2026-10-15）：把 `backend.Dockerfile` 的 apt 段改成清华镜像源（与 pip 同源）：

```dockerfile
RUN (sed -i 's|http://deb.debian.org|http://mirrors.tuna.tsinghua.edu.cn|g' \
        /etc/apt/sources.list.d/debian.sources 2>/dev/null || true) && \
    (sed -i 's|http://deb.debian.org|http://mirrors.tuna.tsinghua.edu.cn|g' \
        /etc/apt/sources.list 2>/dev/null || true) && \
    apt-get update && apt-get install -y --no-install-recommends \
        libpango-1.0-0 libpangoft2-1.0-0 libgdk-pixbuf-2.0-0 fonts-noto-cjk && \
    rm -rf /var/lib/apt/lists/*
```

**验证结果**：`docker compose up -d --build` 全量构建通过，4 个容器全部 Up、MySQL `healthy`，探活 `8080/` / `8000/docs` / `8001/docs` 均 200，MySQL 数据（bind mount）不丢。

**可选加固（方案 A，防将来 pip/npm 也被墙）**：给 Docker 引擎配代理——Docker Desktop → Settings → Resources → **Proxies** → 勾「Manual proxy configuration」→ HTTP/HTTPS 都填 `http://127.0.0.1:7890` → Apply & Restart。配完之后整条链路（apt/pip/npm）都不怕墙。

## 四·六、脚本自身的两处修复（2026-10-15）

`start.ps1` 在修复 apt 源后，又暴露了两个**脚本健壮性**问题，均已修好：

### 1. PowerShell 把 docker 的 stderr 进度当「错误」误终止
脚本顶部原本是 `$ErrorActionPreference = 'Stop'`。PowerShell 5.1 会把 `docker compose build` 打印到 stderr 的**构建进度**当成 `NativeCommandError` 异常，即使 docker 实际成功（exit 0）也会在 `docker compose up -d --build` 处抛中断，导致脚本报「启动脚本执行失败」——**而 8080 其实还能正常访问**。
- 修复：全局改 `'Continue'`（真实失败仍由 `if ($LASTEXITCODE -ne 0)` 判定）；所有 `docker compose` 调用改为 `cmd /c "docker compose ..." 2>$null`，彻底消除红色误报文本。

### 2. 后端冷启动偶发 >60s，探活被误判失败
后端要加载 `deepagents` 库，机器负载高时启动可能 40~70 秒。脚本原本每服务只探活 60 秒，偶发超时误报「启动完成但有服务未通过」。
- 修复：探活超时 `60s → 120s`（前端/认证秒级通过，后端留足余量）。
- 注：后端日志里 `ModuleNotFoundError: No module named 'langchain_fireworks'` 是 `deepagents` 的**可选依赖警告**（非致命，服务照常 200），与启动失败无关。

**最终实测**：连续多轮 `start.ps1` 全量运行，均 exit 0、无红色误报、三服务探活全过（后端 42s 内 200）、4 容器 Up、MySQL healthy。

## 五、卡住了怎么查

启动脚本已在失败时自动打印 `docker compose logs` 尾部并给出命令，顺序按下面走：

| 现象 | 先执行 | 说明 |
|---|---|---|
| 某个容器没起来 / 退了 | `docker compose ps` | 看哪个服务状态不是 Up |
| 想知道它为什么退出 | `docker compose logs -f backend` | 把 `backend` 换成出问题的服务名 |
| 改完还是老样子 | `docker compose up -d --force-recreate backend` | 强制重建该服务 |
| 8080 被别的程序占了 | 脚本会报出**进程名 + PID** | 先关掉那个程序再启动 |
| 提示磁盘不足 | `docker system df` → `docker builder prune` | 见下节 |

**排查命令里的 `backend` 请替换成实际未通过的服务名**（backend / auth / frontend / mysql）。

## 六、磁盘占用（2026-10-15 实测）

`docker system df` 当前结果：

```
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          6         4         7.215GB   6.089GB (84%)
Containers      4         4         1.098MB   0B (0%)
Local Volumes   33        0         7.126GB   7.126GB (100%)
Build Cache     150       0         4.603GB   3.417GB
```

可回收空间合计约 **9.5 GB**，分三档处理，安全程度递减：

| 命令 | 删什么 | 风险 | 建议 |
|---|---|---|---|
| `docker builder prune` | 只删构建缓存（约 3.4 GB） | 低，随时能重新构建 | ✅ 首选，随便执行 |
| `docker image prune` | 悬空镜像（约 6.1 GB） | 低，不影响运行中的容器 | 可执行 |
| `docker volume prune` | 33 个历史匿名卷（约 **7.1 GB**） | **已确认安全**，见下 | 可执行 |
| `docker system prune -af` | 上述全部 | 低，但不可逆 | 确认后再执行 |

> ### ✅ 已核实：删卷不会碰到数据库
>
> 本项目的 **MySQL 数据不走 Docker 卷，而是绑定挂载到宿主机目录**：
>
> | 容器内路径 | 挂载类型 | 宿主机真实位置 |
> |---|---|---|
> | `/var/lib/mysql` | **bind mount** | `D:\ deep_agent search\docker-data\mysql` |
> | `/docker-entrypoint-initdb.d/01-init.sql` | **bind mount** | 项目内 `sql/` 初始化脚本 |
>
> 那 33 个 `ACTIVE=0` 的卷全是 hash 命名的**历史遗留匿名卷**（无容器引用），
> 因此 `docker volume prune` **不会删除任何数据库数据**。
>
> 自查命令（随时可复核）：
> ```bash
> docker inspect das-mysql --format '{{range .Mounts}}{{.Type}} | {{.Destination}}{{println}}{{end}}'
> docker volume ls -q -f dangling=true | wc -l
> ```

> 当前 D 盘余量 **25 GB / 275 GB（已用 92%）**。
>
> **本次已执行的清理**：`docker volume prune` 删除了 15 个历史匿名卷（回收 838 MB），**剩下的 18 个是被其他项目容器引用的，未动**，本项目 MySQL 数据零损失。
>
> **还能继续释放（均安全，可选，非必须）**：
> - `docker image prune`（悬空镜像，约 9.5 GB）—— 下次构建需重新拉取
> - `docker builder prune`（构建缓存，约 5.6 GB）—— 随时能重建，最安全

长期建议——Docker Desktop 默认把镜像、容器、构建缓存全存到**系统盘**：

```
Docker Desktop → Settings → Resources → Advanced → Disk image location → 改到 D 盘
```

## 七、一句话总结

- 日常启动：**双击 `start.bat`**，等它打印「启动成功」，然后开 http://localhost:8080。
- 只改前端：`start.bat -FrontendOnly`。
- 页面没变化：先分清是「浏览器看到的 8080」还是「宿主机 `ui/dist`」，两者要分别重建。
